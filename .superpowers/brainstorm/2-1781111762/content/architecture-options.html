InsightOps 一期架构方向

目标聚焦：配置化 Zabbix 数据接入 + 独立 MySQL 业务库 + Windows 安全日志 RDP 采集 + 虚机基础信息 API

A. 单体后端优先
FastAPI Monolith
Zabbix Reader
RDP Ingest API
VM Asset API
Idle Analyzer
Project MySQL

方案 A：单体后端优先

一个 FastAPI 服务统一承载 Zabbix 读取、RDP 接入、资产管理和分析能力，最利于一期快速落地。

优点

  • 开发和部署最简单
  • 最适合当前仓库从 0 到 1 演进
  • 接口和数据模型容易统一

缺点

  • 后续拆分采集服务需要重构
  • 采集和查询耦合更高
B. API 与采集分离
FastAPI API Service
VM Asset API
Dashboard API
Project MySQL
Collector Service
Zabbix Reader Job
Windows Event Ingest

方案 B：API 与采集分离

查询接口和定时采集分为两个进程或两个服务，共享同一业务库，适合后续扩展为稳定平台。

优点

  • 边界清晰，便于扩展
  • 采集任务不会阻塞 API
  • 后续接多数据源更自然

缺点

  • 编排和配置更复杂
  • 一期工作量高于单体
C. 数据仓层优先
ETL / Sync Layer
Zabbix Sync
RDP Sync
Fact / Dim Tables
FastAPI Read Only
Board / Export / Report API

方案 C：数据仓层优先

先围绕事实表和维表做同步与聚合，API 主要读汇总结果，适合报表强但一期建设成本最高。

优点

  • 报表与分析能力最强
  • 后续指标统一性最好

缺点

  • 建模复杂度最高
  • 对一期快速上线不友好

我的推荐：方案 B。它比方案 A 更利于后续接入前端看板、闲置分析和多种采集器，但又没有方案 C 那么重。
